# Резервная одометрия трамвая — прототип решения

Дата: 26 сентября 2026. Основание: актуальное ТЗ «Резервная одометрия по модели» и приложенный dataset.zip.

## Статус

Реализованы и проверены офлайн модель скорости, обработка ненадёжных колёсных измерений, интегрирование пути, начальная выставка по GNSS и геометрия заданного маршрута. Подготовлены пакеты ROS 2 Humble и адаптер с требуемыми выходными топиками.

**27 сентября 2026: сборка `colcon build --symlink-install` и короткий запуск ROS 2 Humble с реальным bag проверены на этой машине.** Оба пакета собираются; при 15-секундном воспроизведении `dataset/data/30618_af7496f0` с `--clock 100` поступают три входа `/vehicle/*`, GNSS и оба выхода `/result/velocity`, `/result/position`. Числа и логи: `results/demo_runtime/`. Это проверка работоспособности pipeline, не точности положения или всех требований ТЗ. Файл `dataset/COLCON_IGNORE` исключает дубликат пакета сообщений из сборки.

**Без карты невозможно определить дальнейшие повороты по трём скалярным входам.** В комплекте нет реальной карты. Режим без карты удерживает начальное направление и публикует диагностический статус; большие ошибки x/y в этом режиме приведены в отчёте. `example_route.json` — искусственный пример, его нельзя выдавать за карту датасета.

## Что обнаружено в данных

- 122 bag, 8 788 325 сообщений; 97 уникальных файлов БД и 25 точных копий, подтверждено SHA-256.
- Все bag содержат колёсные данные и команду. GNSS master velocity имеется лишь в 86 из 122 bag, rover velocity — в 87; наличие топика в метаданных не означает наличие сообщений.
- README называет скорости колёс м/с, но численные данные соответствуют км/ч. Калибровка только на обучающей части дала множитель **0,2777799848**, практически 1/3,6. Вход переводится в м/с; выход всегда в м/с. Масштаб доступен параметром `wheel_scale`; для действительно метрических входов установить 1.0.
- Команда: int8, диапазон −15…15; знак задаёт торможение/тягу, не направление движения.
- Типичная частота колёс — около 9,8 Гц, команды — 20 Гц. Есть пропуски, дубликаты времени и сообщения с движением времени назад.
- Заголовки входов и времена записи отличаются. В рабочем алгоритме используются заголовки; время прихода определяет доступность информации. Выходные метки сохраняют шкалу времени входных сообщений.

### Координаты без карты

После 3 секунд начальной выставки GNSS не поступает в расчёт движения. Проверена именно эта схема. Удержание начального курса даёт на test bag медиану конечной 3D-ошибки около **4 926 м**, максимум около **9 861 м**. Поэтому текущий режим без карты не решает критерий точности x/y/z на поворотах. Начальная локальная ENU-система построена от первого принятого master fix; начало системы жюри требуется согласовать отдельно.

### Какие тесты выполнены

1. **9 unit-тестов:** постоянная скорость/путь и дубликаты; NaN/Inf/выход за диапазон и старые сообщения; скачок одной тележки и кратковременная блокировка обеих; пропуск и восстановление; большой временной разрыв; запрет GNSS после 3 секунд; поворот и конец известной ломаной; ENU-преобразование; CDR alignment и оба порядка байтов.
2. **7 синтетических сценариев для двух методов:** чистое движение; +5 м/с на передней тележке на 5 с; +5 м/с на обеих на 2 с; блокировка обеих на 1 с; отсутствие обеих на 2 с; потеря задней на 10 с; NaN/Inf. Истинная скорость задана независимой аналитической функцией, шум воспроизводим. Все результаты конечны. Это инъекции ошибок, а не размеченные реальные случаи скольжения.
3. **Причинный replay 20 отложенных реальных bag:** сообщение недоступно раньше записанного времени прихода; GNSS используется после replay для расчёта метрик. При проверке позиции разрешено только начальное окно GNSS.
4. Проверка синтаксиса всех Python-файлов. Проверка вычислительного времени ядра: p95 около 29 мкс на этой машине. Это **не** измерение ROS/DDS-задержки, CPU или памяти целевого окружения.

Разбивка ошибки скорости по режимам (разгон, торможение, равномерное движение, стоянка), графики и сверка живого вывода ROS с офлайн-replay: `docs/VELOCITY_EVAL.md`, `results/velocity_eval/`.

## Сборка и запуск на Ubuntu 22.04 / ROS 2 Humble

Условие: ROS 2 Humble, colcon, rosbag2 и стандартные пакеты сообщений уже установлены. Нода не требует NumPy/SciPy и не скачивает зависимости при сборке или запуске.

Из `/home/iam220904`:

```bash
cd /home/iam220904/rezerv_odometr/tram_odometry_solution
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
export ROS_DOMAIN_ID=73 ROS_LOCALHOST_ONLY=1
ros2 launch tram_odometry odometry.launch.py use_sim_time:=true
```

В другом терминале (остановить через Ctrl+C после короткого фрагмента):

```bash
source /opt/ros/humble/setup.bash
source /home/iam220904/rezerv_odometr/tram_odometry_solution/install/setup.bash
export ROS_DOMAIN_ID=73 ROS_LOCALHOST_ONLY=1
ros2 bag play /home/iam220904/rezerv_odometr/tram_odometry_solution/dataset/data/30618_af7496f0 --clock 100 --rate 1.0
```

Начинайте с обычной скорости воспроизведения 1×. Для нового bag перезапустите ноду; предусмотрен сброс при обратном скачке часов, но ROS bag-loop здесь не проверялся. Начальное окно GNSS задаётся 3 секундами времени Header. После него нода игнорирует GNSS даже при продолжающейся публикации эталона.

| Выход | Тип | Поле |
|---|---|---|
| `/result/velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | `velocity`, м/с |
| `/result/position` | `nav_msgs/msg/Odometry` | `pose.pose.position`, метры; скорость в `twist.twist.linear.x` |
| `/result/diagnostics` | `diagnostic_msgs/msg/DiagnosticArray` | состояние, пропуски, подозрения скольжения, режим геометрии |

Выходная частота задана 20 Гц. Временные метки привязаны к шкале времени входов и продолжаются между сообщениями; при включённом `use_sim_time` остановка `/clock` останавливает продвижение состояния. Режим live: `use_sim_time:=false`. Изменение частоты и остальных параметров при запуске через `ros2 run ... --ros-args -p ...`.

```bash
source /opt/ros/humble/setup.bash
source /home/iam220904/rezerv_odometr/tram_odometry_solution/install/setup.bash
export ROS_DOMAIN_ID=73 ROS_LOCALHOST_ONLY=1
ros2 topic echo /result/velocity --once
ros2 topic echo /result/position --once
ros2 topic hz /result/velocity
ros2 topic hz /result/position
ros2 topic echo /result/diagnostics
ros2 topic echo /result/position --once
```

Для проверки на целевой машине нужно дополнительно измерить время callback→publish и задержку доставки, CPU/RSS в длительном прогоне. `ros2 topic delay` по Header включает задержку источника и шкалу часов; не выдавайте его за чистое время вычисления.

### Короткое измерение производительности ROS 2

27 сентября 2026 выполнен 45-секундный прогон bag `30618_af7496f0` при 1× и `--clock 100`. После 5 с прогрева оба выхода дали 20,00 Гц за окно 20 с. Процесс одометрии: средняя загрузка 13,78% одного ядра (0,138 ядра), максимум по интервалам около 0,5 с — 19,94%; максимальный RSS — 60,99 MB. Выходы продолжались, значения оставались конечными, нода завершилась штатно. Это короткая проверка на текущей машине, не длительный ресурсный тест.

Наблюдатель измеряет задержку от получения каждого входа до следующего полученного выхода с Header не меньше Header входа. Максимум такого **proxy** — 15,80 мс. Принятие конкретного входа оценивателем и точное время публикации в сообщениях не указаны; порядок доставки DDS наблюдателю и ноде может отличаться. Поэтому причинная задержка ≤100 мс и пиковая ≤250 мс остаются **NOT VERIFIED**. Разность Header также не считается временем обработки.

В отдельном ROS_DOMAIN_ID, без уже запущенных ноды и player:

```bash
cd /home/iam220904/rezerv_odometr/tram_odometry_solution
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
export ROS_DOMAIN_ID=74 ROS_LOCALHOST_ONLY=1
python3 tools/measure_performance.py
```

Скрипт сам запускает обычный launch и bag, измеряет и останавливает их. Нужны доступные локальные DDS-сокеты. Ничего не устанавливает и не меняет оцениватель. Результаты перезаписываются в `results/performance/`: `performance.json`, `performance.txt`, исходные наблюдения `samples.json`, логи launch/player. CPU/RSS относятся только к процессу одометрии со всеми его потоками, без player/launch/наблюдателя; пики между опросами `/proc` не измерены. Сохранённый `build.log` относится к исходному проверенному запуску; последующие сборки имеют собственные логи в `log/`.

### Известный маршрут

Поддерживается одна явно заданная упорядоченная 3D-полилиния, без выбора стрелок:

```json
{"origin_lla":[55.0,37.0,150.0],"points_enu":[[0,0,0],[100,0,0],[100,100,0]]}
```

Координаты `points_enu` — восток, север, вверх, метры. Начальная позиция проецируется на маршрут после GNSS-выставки. Неоднозначное пересечение не выбирается молча. Для известного начального пути можно задать `route_start_s` и `route_direction` вручную. В конце полилинии позиция ограничивается концом и выставляется `route_exhausted`. GNSS и скорость в обучение карты автоматически не подмешиваются: реальную карту требуется предоставить отдельно и подтвердить её допустимость у организаторов.

```bash
ros2 launch tram_odometry odometry.launch.py route_file:=/ABSOLUTE/PATH/route.json
```

Параметры `configured_origin`, `origin_latitude`, `origin_longitude`, `origin_altitude` задают общий ENU-origin, если он известен от жюри. Иначе используется origin маршрута или первый принятый master fix. При `allow_initial_gnss:=false` используются настроенные начальные координаты/курс; значение `initial_yaw=0` само по себе не является измеренным направлением.

## Воспроизведение офлайн-проверок

Для офлайн-инструментов нужны Python, NumPy и SciPy; Matplotlib нужен лишь для графиков. Они не требуются рабочей ноде. Установите заранее в отдельном окружении, если отсутствуют. Распакуйте исходный архив: внутри `dataset.zip`, внутри него `data.zip`; в `data.zip` расположены каталоги bag.

```bash
python3 -m unittest discover -s tests -v
python3 tools/audit_dataset.py /PATH/TO/EXTRACTED/DATA --cache /PATH/TO/CACHE --output results
python3 tools/calibrate.py /PATH/TO/EXTRACTED/DATA /PATH/TO/CACHE --output results --config src/tram_odometry/config/model.json
python3 tools/evaluate.py /PATH/TO/CACHE --splits results/splits.json --config src/tram_odometry/config/model.json --split test --output results/reproduced_test
python3 tools/stress_test.py
```

Калибровка повторно создаёт model.json только по train; состав test не используется для подгонки. Исполняемое ядро одинаково у офлайн replay и ROS-адаптера. Короткая проверка ROS/DDS выполнена; длительная нагрузка и задержки не измерялись.

## Что остаётся до сдачи

- Сборка и короткий запуск в ROS 2 Humble проверены; перед показом запускать ноду и bag в одном ROS_DOMAIN_ID.
- Получить допустимую карту/маршрут и точное определение системы координат эталона. Уточнить, разрешено ли строить карту из обучающей GNSS-телеметрии; комплект этого разрешения не предполагает.
- Подтвердить у организаторов противоречие единиц входной скорости с README.
- Измерить задержку ≤100 мс, частоту ≥10 Гц, CPU ≤2 ядра и память ≤0,5 ГБ в их окружении. Измерения ядра этих требований не подтверждают.
- Заполнить имя/контакт владельца в package.xml/setup.py; сейчас стоят явно технические `example.invalid`.

Описание модели: `docs/MODEL.md`. Исходные определения сообщений взяты из архива организаторов; добавлены явный поиск ament_cmake, экспорт runtime и обязательное поле maintainer для сборки. Новая реализация не публиковалась в открытом репозитории.
